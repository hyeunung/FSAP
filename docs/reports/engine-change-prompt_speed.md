엔진 작업이다. MechDesign_Engine(v3.3.0)을 고친다. 주제는 **실행 속도**다. 실제 프로젝트 실행에서 과제 하나에 3~5시간이 걸렸고, 그중 형상을 그린 시간은 10분 안팎이었다. 나머지는 검사, 다시 열기, 다시 조사에 들었다. 프로젝트 파일은 이 PC에 없으니 찾지 말고 아래 내용만으로 고친다. 엔진은 범용이다. 특정 프로젝트·부품·형번·사이트 이름을 엔진 문서에 넣지 않는다. 개선후보 번호는 엔진의 다음 번호로 받는다.

## 0. 관찰한 사실(한 과제 기준, 바디 약 270개·설계 파일 약 12 MB)

| 단계 | 걸린 시간 | 실제로 한 일 | 낭비 |
|---|---|---|---|
| 측정부 | 26분 | CLI를 16번 불렀다(실제 측정 작업은 약 7개). 부를 때마다 설계 파일을 처음부터 다시 열었다(1회 3~5분) | 대부분이 파일 다시 열기 |
| 구상 3안(동시) | 14분 | 구매품 형번(볼나사·지지 유닛·커플링·서보)을 '미정'으로 넘겼다. 구매 사이트가 로그아웃 상태였다 | 선정 단계로 일이 밀림 |
| 선정 PM | 12분 이상 | 구매 사이트를 약 40번 열어 형번을 하나씩 검색·상세 조회 | 동시에 도는 구상에서 할 일을 혼자 하는 단계가 함 |
| 모델링(다른 과제) | 7분 | 판 두 장 두께 ±5 mm, 구멍 몇 개 | — |
| 모델링 뒤 검사 | 3분 + 42분 이상 | 바뀐 판 주변 틈을 조인트 양 끝에서 3분에 확인. 그 뒤 기계 한 사이클 전체 동작 간섭을 움직이는 부품 7묶음 전부로, 제한 시간 2시간을 걸고 **앱(MCP)에서** 돌림. 앱이 멈춰 사용자가 앱을 껐다 | 바뀐 것과 무관한 전체 검사, 앱 점유 |
| 과제끼리 | 직렬 | 서로 닿지 않는 과제도 하나씩 돈다 | 동시 실행 없음 |

원인은 CAD(CLI·MCP)의 한계보다 **필요 이상 검사하고, 같은 파일을 여러 번 다시 열고, 앞 단계에서 정할 것을 뒤로 미루는 절차**에 있다.

## 1. 검사 범위를 과제 크기에 맞춘다 (가장 큰 효과)

- 지금: 과제마다 합격 기준이 "동작 연구 전 구간 간섭 0"으로 똑같다. 판 두께만 바꾼 과제도 기계 전체 사이클을 다시 돈다.
- 바꿀 것:
  1. **과제 안 검사 = 바뀐 것만.** ledger scope(새로·바뀜·없어짐 바디)와 그 주변(바운딩 상자 + 여유 거리 안 바디)만 대상으로 한다. 관련 조인트의 양 끝·중간 몇 점(예: 0·25·50·75·100 %)에서 `inspect.clearance`/`inspect.interference`로 잰다. 관련 조인트는 바뀐 바디가 속한 컴포넌트를 움직이는 조인트와, 주변 바디를 움직이는 조인트다.
  2. **전체 사이클 간섭 검사 = 라운드 끝 한 번.** 최종 회귀에서만 한다. CLI로 저장본에 대고, occurrences 또는 단계 범위를 나눠 병렬로 돌린다.
  3. **오래 걸리는 계산은 앱(MCP)에서 돌리지 않는다.** 예상 시간이 몇 분을 넘는 `motion.interference`·전체 간섭은 CLI로만. 앱은 그리기·저장·짧은 확인에만 쓴다. 앱이 멈추면 사용자가 모델링을 볼 수 없고, 앱을 끄면 그때 돌던 명령이 실패한다.
  4. 합격 기준 문구를 "과제 범위 간섭 0(과제 안) + 전체 사이클 간섭 0(라운드 끝 회귀)"로 나눈다. 과제 정리부·검도·최종 회귀 지시문과 R2 완료 조건 ③을 맞춘다.
- 시험: 바디 하나만 바뀐 가짜 과제에서 과제 안 검사가 전체 사이클을 부르지 않는지, 라운드 끝 회귀는 부르는지.

## 2. CAD 통로: 파일은 한 번만 연다

- 지금: L1 '부서 지시문'은 모델링부만 MCP, 나머지 부서는 CLI다. 그래서 혼자 도는 측정부도 CLI로 큰 파일을 여러 번 다시 연다. MCP 우선 규칙(앱이 켜져 있으면 MCP)은 모델링부에만 걸려 있다.
- 바꿀 것:
  1. **그 시각에 CAD를 쓰는 부서가 하나뿐인 단계**(측정부, 검도, 최종 회귀의 짧은 측정)는 MCP로 저장본을 한 번 `open` 하고 그 세션에서 연속으로 잰다. 저장하지 않는다(`save` 금지). 끝나면 동작 상태를 초기화한다. 단 1-3의 '오래 걸리는 계산'은 CLI.
  2. **동시에 도는 부서**(구상 여러 안, 문서·체결·해석 job)는 MCP를 쓰지 않는다. 앱 세션 하나를 여럿이 쓰면 열린 문서가 엉킨다. 이들은 CLI로 하되 **잴 것을 스크립트 하나로 묶어 저장본을 한 번만 연다.**
  3. 같은 저장본을 반복해서 열어야 하면 측정 결과 JSON을 공유 파일로 남기고 다른 부서는 그것을 읽는다.
  4. 부서 보고서에 'CAD 통로(MCP/CLI), 호출 수, 파일 열기 수, 걸린 시간'을 적게 한다(5절).
- 안내서(engine/cad/solidcraft.md) '연결' 절과 L1 '부서 지시문'을 함께 고친다.

## 3. 측정을 다시 쓴다

- 지금: 과제마다 측정부가 모델 전체(바디 전수 bbox·부피·위치)를 처음부터 다시 잰다.
- 바꿀 것: 앞 과제·앞 라운드의 측정 표(바디별 bbox·부피·질량·컴포넌트)를 저장해 두고, ledger 차이(새로·바뀜·없어짐)만 다시 잰다. 측정 표에는 기준 버전 파일 이름과 해시를 적어 맞는 판인지 확인한다. 해시가 다르고 ledger도 없으면 그때만 전수 측정한다.

## 4. 구상 단계에서 구매품을 정해 넘긴다

- 지금: 구상안이 구매품 형번·카탈로그 값을 '미정'으로 넘겨도 된다. 그러면 선정 PM이 혼자서 사이트를 수십 번 연다.
- 바꿀 것:
  1. 구상부 결과 스키마에 구매품마다 `part_no`(형번), `catalog_values`(판정에 쓴 허용치: 예 볼나사 골지름·허용 회전수·정격 하중, 서보 정격 토크·회전자 관성), `source`(카탈로그 URL·페이지)를 필수로 넣는다.
  2. 값을 못 구하면 비워 두지 말고 E-12 임시값을 적고 `provisional: true`와 자료대기 후보로 표시한다.
  3. 선정 PM은 **비교·판정만** 한다. 새 조사는 하지 않는다. 임시값 때문에 판정이 갈리면 그 사실을 적고 임시값으로 판정한다.
  4. 구상안이 같은 구매품을 각자 조사해 중복이 생기지 않게, 과제 정리부(또는 준비 점검부)가 과제에 필요할 구매품 종류를 미리 적고, 구상 시작 전에 한 부서가 카탈로그 표를 한 번 만들어 구상안들이 함께 읽게 하는 방법도 된다.

## 5. 구매 CAD를 못 받으면 기다리지 않는다

- 지금: 로그인 풀림·봇 확인 페이지·사이트 오류로 STEP을 못 받으면 부서마다 다시 시도하거나 조사로 시간을 쓴다.
- 바꿀 것:
  1. 못 받으면 즉시 카탈로그 외형 치수(규격표·외형도)로 `STEP대기_<형번>` 임시 형상을 그리고 과제를 계속한다. 같은 과제 안에서 다시 시도하지 않는다.
  2. 실물 교체는 라운드 시작·끝의 'STEP 대기 재시도' 단계가 한다(이미 있는 단계).
  3. 봇 확인 페이지는 통과하려 하지 않는다. 결과에 `login`/`blocked` 상태를 적고 최종 보고 맨 위에 올린다.

## 6. 과제 크기에 맞춘 절차

- 지금: 작은 수정(구멍 하나, 판 두께, 공구 자리)도 측정 → 구상 3안 → 선정·감사 → 모델링 → 검도 → 해석을 모두 거친다. 작은 과제 하나에 약 4.7시간 걸린 적이 있다.
- 바꿀 것:
  1. 과제 정리부가 과제마다 크기 등급을 매긴다. 예: `S`(기존 부품 치수·구멍·자리 수정, 새 구매품 없음, 조인트 변화 없음), `M`(부품 몇 개 추가·교체), `L`(새 구동 유닛, 새 조인트·동작 연구).
  2. `S`는 구상 1안(대안 비교 생략), 해석은 손계산으로만, 선정·감사는 한 부서로 합친다. `M`·`L`은 지금처럼 한다.
  3. 등급과 근거를 과제 표에 적고, 검도가 결과를 보고 등급이 틀렸으면(예: S인데 새 구매품이 생김) 다음 라운드 과제로 다시 올린다.
- 품질 기준(SF, 간섭 0, 체결 결함 0)은 등급과 상관없이 같다. 줄이는 것은 대안 수와 절차뿐이다.

## 7. 서로 겹치지 않는 과제를 동시에 돌린다

- 지금: 과제는 직렬이다. 각 과제가 앞 과제가 저장한 버전 위에서 그리기 때문이다. 버전 파일 둘을 합치는 방법이 없다.
- 해결 방향: **파일을 합치지 않고, 각 과제가 실행한 편집 명령을 기록했다가 기준 파일에 차례로 다시 실행한다.**
  1. **발자국(footprint).** 과제 정리부가 과제마다 `bodies`(건드릴 바디·컴포넌트 이름), `envelope`(쓸 공간 좌표 상자, 동작 범위 포함), `joints`(바꿀 조인트·동작 연구)를 적는다.
  2. **묶음 고르기.** 발자국의 바디·공간이 서로 겹치지 않고, 조인트·동작 연구를 바꾸지 않는 과제끼리 한 묶음으로 동시에 돌린다. 조인트·연구를 바꾸는 과제, 구매품을 다른 과제와 공유하는 과제는 처음엔 묶음에서 뺀다(직렬).
  3. **같은 기준에서 작업.** 묶음의 과제는 모두 같은 기준 버전의 복사본(`tools/out/<과제>/base.sc`)에서 시작한다. 앱은 하나뿐이니 동시 과제의 모델링은 CLI로 한다.
  4. **편집 명령 기록.** 모델링부는 실행한 명령을 순서대로 `tools/out/<과제>/edit.json`(명령 스크립트 JSON 배열)에 남긴다. 탐색용 명령·되돌린 명령(undo)은 빼고, 최종 결과를 만드는 명령만 남긴다. 그 스크립트를 기준 파일에 `run --in base --save <후보>`로 다시 돌려 과제 결과와 같은지(바디 이름·부피·bbox) 모델링부가 확인한 뒤 끝낸다.
  5. **합치기.** 합치기 단계가 기준 파일에 과제 A, B …의 edit.json을 차례로 다시 실행해 새 버전 하나로 저장한다. 실패한 과제는 빼고 다음 라운드 직렬 과제로 돌린다. 합친 파일에서 발자국 경계 간섭 검사를 한 번 하고, 앱(MCP)으로 열어 사용자가 보게 한다.
  6. **문서.** 결정로그·BOM·설계검토서는 과제별 조각으로 써 두고 합치기 단계가 차례로 붙여 커밋 하나로 남긴다. 버전 번호는 합친 결과만 받는다. 과제별 후보 파일은 `tools/out/`에 둔다(납품 STEP 규칙 E-06과 같은 취지).
  7. **먼저 확인할 것(구현 전 시험).** 명령 재실행이 같은 결과를 내는지 확인한다. 특히 구매품 STEP 넣기(import), 면을 좌표로 집는 명령(offset_face·fillet 등), 컴포넌트 활성화, 타임라인 삭제가 재실행에서 같은 결과를 내는지. 이미 끝난 과제 하나의 명령을 뽑아 그 과제의 기준 버전에 다시 실행해, 결과 버전과 바디 목록·부피·bbox가 같은지 본다. 다르면 그 명령 종류는 동시 묶음에서 쓰지 않는 규칙으로 둔다.
- full_run에 들어갈 곳: 과제 정리부 결과 스키마(footprint, size), 라운드 안 '묶음 고르기 → 묶음 병렬 → 합치기 → 묶음 경계 검사' 단계, 실패 과제 직렬 복귀. 가짜 에이전트 시험에 '겹치지 않는 두 과제 동시·합치기 성공', '한 과제 재실행 실패 → 직렬 복귀'를 넣는다.

## 8. 시간 기록

- 부서마다 결과에 `elapsed_s`, `cad_calls`, `file_opens`, `channel`(MCP/CLI), `browser_calls`를 적는다.
