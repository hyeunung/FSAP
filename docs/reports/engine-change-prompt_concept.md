## 0. 관찰된 사실(실측, 한 프로젝트 하루 실행)

| 항목 | 값 |
|---|---|
| 실행 시간 | 약 16.5시간, 과제 10개(구동 과제 + 구동 후보) |
| 부서별 시간 | 모델링 5.8 h, **구상(기구설계부 3명) 3.5 h, 선정(PM·감사) 2.3 h**, 전체 회귀 2.4 h, 검도 2.0 h, 측정 1.4 h |
| 구상 결과 | 요구서 0-8(전체 구동 개념)이 사용자 동의로 확립돼 있고 유닛마다 벤치마크가 적혀 있는데도, 과제마다 3안을 만들었다. 3안의 차이는 새 아이디어가 아니라 같은 개념 안의 배치·치수였다. 벤치마크 안(1안)이 기각된 이유도 개념이 아니라 치수 문제(틈 1 mm, 띠 안 벽 등)였다 — 같은 설계자가 고치면 되는 것 |
| 원인 | `modeling_round.js`가 기구설계부 3명을 무조건 병렬로 돌린다(방향 3개 고정). v3.7.0 WF-154는 '고르는 기준'만 바꿨고 '몇 안을 만드는지'는 그대로다 |
| 버전 번호 | 과제마다 새 유닛(부품 묶음)을 만들었는데 버전은 늘 마지막 자리만 올랐다(v1.0.2 → v1.0.16). L1 E-05 "부품 묶음 신설·삭제는 가운데 자리"가 적용되지 않았다 |
| 회귀 | 두 번째 전체 회귀가 전체 상한 30분에서 끊겼다. 원인: 조인트 10개를 몬 '자세' 한 점이 연구 한 단계보다 훨씬 느린데(16병렬에서 점당 약 18 s), 시험 실행을 연구 묶음으로 해서 어림(955 s)이 자세를 과소평가했다. 자세 25점 묶음이 호출 상한 480 s를 30번 넘겼다 |

사용자 원칙(원문): "벤치마킹 하기로 했는데 왜 구상안이 3개나 있는거야?", "2,3은 벤치마킹이 있던 없던 상관없는거 아니야?", "색다른 아이디어를 내는구간이 아니잖아".

## 1. 구상 단계: 개념이 확립되면 1명만(우선순위 1)

- **0-8이 확립(0-8-6 동의)된 프로젝트에서는 과제마다 기구설계부를 1명만 돌린다.** 벤치마크가 있든 없든 같다. 새 아이디어를 내는 단계는 0-8에서 끝났고, 과제 단계는 그 개념을 이 기계 치수에 맞게 상세 설계하는 일이다.
  - 벤치마크가 있는 유닛: 0-8-3의 '그대로 가져오는 벤치마크'를 그대로 옮겨 이 기계 치수로 상세 설계한다.
  - 벤치마크가 없는 유닛: 0-8-3의 '새로 하는 것'과 0-8 개념대로 1안을 상세 설계한다.
- **막히면 같은 설계자가 고친다.** 측정·완료 판정·검도에서 안 되는 곳이 나오면 다른 안을 새로 만들지 않고 그 설계자가 그 자리만 고쳐 다시 낸다(수정 횟수 상한은 지금의 수정 회차 규칙을 따른다).
- **선정(PM·감사) 단계는 없앤다.** 안이 하나이므로 비교할 것이 없다. 남는 것은 완료 판정 확인 하나(지금 감사의 '완료 판정 만족' 검사만 남긴다).
- **예외(여러 안):** 0-8이 확립되지 않은 프로젝트(E-01상 어차피 엔진을 돌리지 않음), 또는 1안이 개념 자체로 안 된다는 근거(물리적으로 불가, 행정 부족 등 치수로 못 푸는 것)가 나와 사용자가 개념 재검토를 승인한 경우에만 2안 이상을 낸다. 이때도 0-8 개념 바꾸기는 사용자 동의가 먼저다(E-02).
- `modeling_round.js` 구상 단계(지금 `conceptPrompt` × 3, 방향 3개 고정)와 선정 단계를 위처럼 바꾸고, 결과 스키마의 '방안 비교 표'는 '설계안 1개 + 고친 이력'으로 바꾼다.
- 결정로그 기록 형식도 '방안별 판정 표' 대신 '설계안 · 고친 곳 · 이유'.

## 2. 버전 번호: 가운데 자리를 실제로 올리기(우선순위 2)

- L1 E-05 "작은 형상 변경은 마지막 자리 +1, 구동 방식·개념 교체나 부품 묶음 신설·삭제는 가운데 자리"를 워크플로우가 지키게 한다.
- 합치기부·모델링부가 새 번호를 정할 때 판정한다: 이번 저장에서 새 컴포넌트(유닛·부품 묶음)가 생기거나 없어졌으면 가운데 +1·마지막 0, 아니면 마지막 +1. 판정 근거(새로 생긴·없어진 컴포넌트 이름)를 결과 `version_reason`에 적는다.
- 과제 하나 안의 수정 회차(수정 1·2회차)는 같은 과제의 작은 변경이므로 마지막 자리.
- 시험에 '새 컴포넌트가 생긴 저장은 가운데 자리가 오른다'를 넣는다.

## 3. 전체 회귀: 자세 묶음을 따로 어림하고 작게 나누기(우선순위 3)

- 시험 실행(20단계)을 연구 묶음 하나로만 하지 않는다. **연구 묶음과 자세(조인트 여러 개를 동시에 몬 점) 묶음을 각각 시험**하고, 어림을 둘로 나눠 더한다(`timing`에 연구 단계당·자세 점당 시간 따로).
- 자세 묶음 크기는 시험값으로 정한다: 묶음 하나의 어림이 호출 상한의 절반 안에 들게(예: 점당 18 s면 12점 안쪽). 고정 개수로 두지 않는다.
- 어림 합이 전체 상한을 넘으면 시작 전에 범위를 줄이고 '못 본 범위'를 먼저 정한다(끊기고 나서 정하지 않는다). 지난 회귀의 못 본 범위를 맨 앞에 둔다(지금 규칙 유지).

## 4. 마무리

- 버전을 올리고 CHANGELOG에 WF 번호로 적는다.
- 시험(test_fake_agents.js): ① 0-8 확립 프로젝트에서 구상 에이전트가 1명만 뜨고 선정 단계가 없는지 ② 1안이 막혔을 때 같은 설계자 수정으로 가는지 ③ 새 컴포넌트 저장 시 가운데 자리 ④ 회귀 시험이 연구·자세 둘 다 하는지.
- 우선순위: 1(구상 1명·선정 폐지) → 2(버전) → 3(회귀 자세 묶음).
